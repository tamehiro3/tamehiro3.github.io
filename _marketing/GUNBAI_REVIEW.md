## 1. フェーズ判定

**判定: P0（打席前）と P1（手動運用）の境目。迷ったら下を取る規則により P0 寄りとして扱う。**

軍配の処方では、P0 の「やらないこと」に**自動化**が入っています（core.md §3 / automation.md §6）。理由は「自動化の検討が、売る打席に立たない言い訳になりやすい」から。一方で P0 の処方には SNS運用（x-ops）そのものは含まれています。

そこで今回の裁定資料は次のとおりです:

- 自動化してよいのは Green の反復作業だけ（検品・承認済み在庫の定時消化・記録・警報・自動停止）。原稿は必ず本人の声（Typeless）から。
- 自動化の建築は今回の1回で打ち止め。計測の自動取得・ダッシュボード・複数SNS対応は作らない（§6 やらないこと）。
- 仕組みの目的は「毎日出す」を根性でなく構造で守ること（automation.md §0「人力で維持できる基準値は基準値ではない」）。日曜15分で7本話せば1週間回る設計にして、打席の回数を増やす側に効かせる。

## 2. KPI宣言

```
■ KPI宣言: Typeless音声下書き → 検品 → 承認 → 毎日1本の自動投稿
- 動かすKPI: 仮ノード「週の投稿本数」（目標7。先行指標）→ その先の北極星「ゲームのプレイ人数」は未計測（穴）
- 変化への接続（仮・本人確認待ち）: 課金や個人情報の心配なく、親子や大人が毎日数分いっしょに頭を使う時間を持てるようになる
- 仮説: 話すだけで下書きになり、検品と投稿が自動なら、週1回15分の作業で毎日の投稿が途切れなくなる
- 根拠: 勘（本人の投稿頻度・反応の実績データはまだない）
- やらないことリスト照合: 抵触なし（§6）。ただしフェーズ上は「自動化」が要注意 → §1 の条件つきで進める
- 検品予定: 投稿文は毎回、機械検品＋本人の4項目チェック（文体・事実・リーガル・プライバシー）
- 計測: 毎週日曜の「週次改善」Issue（自動集計＋手で写す数字＋所見一言）。4週後に継続/変更/撤退を裁定
```

「変化の一文」はサイトの文面から組み立てた仮のものです。ポジショニングとして本人が確認・修正してください（本人判断事項 §8）。

## 6. やらないことリスト

| 施策 | 理由 |
|---|---|
| AIが投稿文を自動生成して流す | 信号色 Red（原稿の魂）。Typeless の整形は本人の発話の変換にとどめ、承認を必ず挟む |
| 自動いいね・自動フォロー・自動リプライ・自動メンション | X自動化ルール。凍結はアカウントという資産の没収（funnel §4-1） |
| リポスト・フォローで抽選などの懸賞 | X規約と景品表示法の両方の確認が必要。自動投稿では扱わない |
| 複数SNSへの同時投稿 | 1チャネル集中（core §3）。主戦場が回ってから検討 |
| 同じ文面の再投稿 | X規約（重複コンテンツ）。二重投稿防止 |
| SNSの数字をAPIで自動取得するダッシュボード | P0〜P1では過剰装備。Xは読み取りも課金。週次の手動写しで足りる |
| プレイ人数などの数字を投稿に書く | 出典になる計測がない（事実台帳） |

## 7. 出荷検品（review-protocol §5）

今回の出荷物は**仕組み**（コード・設定・文書）です。投稿文は含みません（投稿文は毎回このパイプラインの検品を通ってから出ます）。

| 検品 | 結果 |
|---|---|
| 機械 | 単体テスト58件すべて通過。ワークフローとIssueフォームのYAML構文を検証。文書・設定・コードに異言語文字（キリル・ハングル・簡体字）の混入なし |
| 試運転（初回手動実行） | 手元の使い捨てリポジトリで、下書き→検品コメント→承認→在庫コミット→ドライラン→本番投稿（SNS部分のみ模擬）→記録コミットまで通しで実行。push競合からの自動再送も確認。F13 の不具合を発見して修正 |
| 事実 | 事実台帳の各項目を index.html / privacy.html の該当行と照合（行番号つき）。新しい事実の追加はなし |
| リーガル | 投稿文の事前選別ルールを整備（景品表示法・X規約・NFT関連）。これは適法性の保証ではなく事前選別。判断に迷う投稿は「要専門家確認」として出さない |
| 文体 | 文書は本人の確認待ち（とくに「変化の一文（仮）」と輪番表のお題） |

**未完了のもの**（本人の作業が要る）: GitHub Actions 上での初回手動実行、公式ページでの料金・規約の再確認、Windows での「★サイトを公開する.bat」の動作確認（F14）、§8 の裁定。

## 9. 追加点検：画像つき投稿（Canva × Issue添付）— 2026-09-26

対象: 下書きIssueへの画像添付、画像の文字の検品、X / Bluesky への画像アップロード。深さは常法。API の確認だけ深掘。

### 9.1 宣言

```
■ KPI宣言: Canvaで作った画像を付けた投稿（主に「今日の謎」カード）
- 動かすKPI: 仮ノード「投稿あたりの反応（いいね・返信・保存）」。北極星「プレイ人数」は引き続き未計測（穴）
- 変化への接続: 謎を一目で読める形にして、親子や大人が「解いてみよう」と手を止めるきっかけを増やす
- 仮説: 謎は文字だけより画像のほうが目に留まる
- 根拠: 勘（画像つき・なしを比べた実績はまだない）
- やらないことリスト照合: 抵触なし（§6・§9.5）
- 検品予定: 投稿文＋画像の説明（本人の申告）を機械検品、OCRで画像の中の文字を照合、本人の「画像」チェック
- 計測: 週次改善Issueで画像つき／なしの反応を並べる。画像つきは週1〜2本なので、30本たまるまでは「観測中」（automation §4）
```

フェーズは引き続き P0 寄りです。装備を増やしすぎないよう、1投稿1枚・PNGとJPGだけ・動画なしに絞りました。

### 9.4 点検の指摘と対処

| # | 指摘 | 根拠 | 対処 | 状態 |
|---|---|---|---|---|
| H1 | XのAPIで画像を上げられるか未確認のまま作り込むと、量産後に壁に当たる | automation §5 | 画像つきX投稿は初期値で無効。疎通確認コマンドとワークフローを用意。無効のままXで画像つき下書きを出すと、受付の時点で止める | 反映済み |
| H2 | OCRは誤読する（試験画像で、大きな装飾見出しを「SAE」などと誤読。JPGだとさらに悪化） | review-protocol §2（機械で決められることだけ機械で決める） | 合否は本人の「画像の説明」で決める（投稿文と同じルールで検品）。OCRは2通りの読み方を合わせ、説明との一致率が50%未満なら要確認 | 反映済み |
| H3 | 試運転で発見: 説明に書かずに画像へ「日本一」「広告なし」を入れても、OCRが検出したのに承認できていた | review-protocol §5（検品なしに出荷しない） | OCRが**3文字以上の禁止表現**を検出したら承認を止める。短い一致（IQ など）は誤読で出やすいので要確認のまま | 修正済み・テスト済み |
| H4 | スマホの写真には撮影場所（GPS）が入っていることがある。子ども向けサイトの発信では特に危険 | funnel §4-5（プライバシーの既定） | 位置情報入りの画像は承認を止める。撮影情報（EXIF）だけなら要確認 | 反映済み・テスト済み |
| H5 | 画像の説明（代替テキスト）がないと、目の不自由な人に届かない。検品の材料もない | x-ops §4（メディアの品質） | 画像を付けたら説明は必須。Xは代替テキストを設定（失敗しても投稿は続ける）、Blueskyは埋め込みに付ける | 反映済み |
| H6 | 承認後に画像が差し替わると、確認していない画像が出る | x-ops §4（素材は不変名で） | 承認時に画像をダウンロードして `media/` に不変名で保存し、ハッシュを記録。投稿時にハッシュが違えば保留 | 反映済み・テスト済み |
| H7 | 任意のURLから画像を取りに行くと、悪用や事故のもと | 安全 | 取得するのは GitHub の添付URLだけ。転送先も GitHub の配信ドメインに限定。サイズ上限つき。所有者以外の下書きの画像は取得しない | 反映済み・テスト済み |
| H8 | どの投稿の画像か分からなくなる | x-ops §4（1投稿1話題） | 画像つきの下書きは投稿文1本・画像1枚まで | 反映済み |
| H9 | 画像はリポジトリに溜まり続ける（公開リポジトリなので誰でも見られる） | 安全・運用 | Pages には出ない（`_marketing/`）。1枚100KB前後なら年に数MB。公開で困る画像（顔・個人情報）は検品チェックで止める | 記録のみ |

### 9.5 やらないこと（追加）

| 施策 | 理由 |
|---|---|
| AIが画像を自動で作ってそのまま投稿する | 信号色 Red（原稿の魂）。Canvaで作るのは本人、または本人が確認したものだけ |
| 動画・GIF・複数枚の投稿 | P0寄りで装備過多。1投稿1枚の静止画で反応を見てから |
| 画像の自動圧縮・自動加工 | 承認した画像と投稿される画像が変わってしまう。大きすぎる画像は止めて、書き出し直してもらう |
| Xの認証を OAuth 2.0 に作り替える | 更新のたびに変わる鍵を保存するため、GitHub の強い権限の鍵（Secrets を書き換えられるトークン）が必要になる。疎通確認が失敗したときに改めて本人判断 |
