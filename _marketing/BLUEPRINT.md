# 設計図：Typeless × SNS自動投稿（しのびのゲーム工房）

- 版: 2026-09-26（初版）
- 状態: **実装済み・本番OFF**（`_marketing/sns/config.json` の `mode: dry-run`）
- 点検: [GUNBAI_REVIEW.md](GUNBAI_REVIEW.md)（軍配 v2.3 で点検。指摘はこの設計図に反映済み）
- 使い方: [README.md](README.md)

## 0. ひとことで

**話す（Typeless）→ 置く（GitHub Issue）→ 機械が検品 → 自分で承認 → 毎日20:17に1本ずつ自動投稿 → 週1回、数字を見る**

Typeless は音声を整った文章に変えて、スマホやPCのどの入力欄にも打ち込めるアプリです。投稿を外部へ送るAPIはありません。そこでこの設計では Typeless を**入力の道具**と位置づけ、下書きの受付から先（検品・承認・予約・投稿・記録）を GitHub の仕組みで自動化します。

## 1. 全体図

```
[あなた] スマホ / PC
   │  Typelessで話す（音声 → 整った文章）
   ▼
① 受付箱  GitHub Issue「SNS下書き」フォーム（ジャンルとリンク先はプルダウン）
   │  自動: 機械検品（文字数・禁止表現・リンク・異言語・数字の照合・重複）→ 結果をコメント
   ▼
② 承認    本文の「検品チェック」4つに✓ → ラベル「承認」          ← 人間の仕事
   │  自動: 再検品してOKなら在庫へコミットしてIssueを閉じる / NGなら差し戻し
   ▼
③ 在庫    _marketing/sns/queue/*.json（先に承認したものから順に）
   │  自動: 毎日 20:17 JST に1本
   │        在庫 → sending/ に確保（コミット）→ 投稿 → posted/ に記録（コミット）
   │  守り: 1日1本まで・月の予算上限・二重投稿防止・在庫7本割れで警報Issue
   ▼
④ SNS     主戦場は1つだけ（X または Bluesky。config.json の channel）
   ▼
⑤ 週次    毎週日曜 21:07 に「週次改善」Issue（自動集計）
           → 数字を写して所見を一言 → 裁定を ledgers/DECISIONS.md に1行
```

## 2. 誰が何をするか（軍配の信号色）

| 工程 | 担当 | 信号色 | 自動化レベル |
|---|---|---|---|
| 投稿文を話す（原稿の中身） | あなた（Typeless） | Red（自動化しない） | L3 手動 |
| 機械検品・結果のコメント | GitHub Actions | Green | L1 候補（初回の本番確認後に昇格） |
| 承認（出してよいかの判断） | あなた | Yellow | L2 |
| 在庫への投入・定時投稿・記録 | GitHub Actions | Green（承認済みだけを消化） | L1 候補 |
| 在庫切れ・失敗・予算超過の警報と自動停止 | GitHub Actions | Green | L1 候補 |
| 週次の集計 | GitHub Actions | Green | L1 候補 |
| 数字の書き写し・所見・改善案の裁定 | あなた | Yellow | L2 |
| 主戦場・予算・本番開始の決定 | あなた | Red | L3 |

AIが投稿文を自動で書いて流すことはしません。原稿はあなたの声、仕組みはそれを毎日届けるための増幅器です。

## 3. 部品一覧

| 場所 | 役割 |
|---|---|
| `.github/ISSUE_TEMPLATE/sns-draft.yml` | 受付箱（下書きフォーム） |
| `.github/workflows/sns-inbox.yml` | 下書きの検品と、承認→在庫投入 |
| `.github/workflows/sns-post.yml` | 毎日の定時投稿（手動実行は既定でドライラン） |
| `.github/workflows/sns-weekly.yml` | 毎週日曜の週次改善Issue |
| `.github/workflows/sns-test.yml` | ツールのテストと在庫の再検品 |
| `_marketing/sns/config.json` | 本番スイッチ（mode）、主戦場（channel）、予算、リンク先 |
| `_marketing/sns/rules.json` | 禁止表現（block）と要確認表現（warn）、理由つき |
| `_marketing/sns/tool/` | 検品・投稿のプログラム（Python標準ライブラリのみ） |
| `_marketing/sns/queue/` → `sending/` → `posted/`（`held/`） | 在庫 → 送信中 → 投稿済み（保留） |
| `_marketing/OFFER_FACTS.md` | 事実台帳（投稿に使ってよい事実） |
| `_marketing/ledgers/DECISIONS.md` | 判断ログ（追記のみ） |

`_marketing/` はフォルダ名が `_` で始まるため、GitHub Pages（Jekyll）では公開サイトに出ません。ただしリポジトリ自体は公開なので、GitHub上では誰でも読めます（点検 F3）。

## 4. 投稿の型

### 4.1 基本ルール
- **1投稿1話題・1リンク**。URLは話さず、フォームの「リンク先」で選ぶ（許可したリンク先以外は通らない）。
- **ハッシュタグは2個まで**、**@メンションは使わない**（自動投稿でのメンションはXの自動化ルール上の要注意事項）。
- 数字・実績は[事実台帳](OFFER_FACTS.md)にあるものだけ。台帳の「言ってはいけないこと」（広告なし、効果の断言、No.1、期間限定など）は機械検品で止まる。
- SNSで話しかける相手は**保護者と大人**。子ども本人に向けた呼びかけはしない。子どもの名前・学校・顔は出さない。

### 4.2 輪番表（日曜にこの順で7本話す）

在庫は先に承認したものから順に出るので、月曜の分から順番に話せば曜日どおりに投稿されます。

| 曜日 | ジャンル | 話すお題の例 | 角度 | CTA | リンク |
|---|---|---|---|---|---|
| 月 | 今日の謎 | ゲームに出てくるタイプの謎を1問（答えは次の投稿で） | practice | ソフト | なし |
| 火 | 親子で | 子どもと遊んだときの一言や反応（個人が分かる情報は出さない） | proof | ソフト | なし |
| 水 | 作り手の話 | 今週作ったところ・直したところ・迷ったこと | mechanism | ソフト | なし |
| 木 | 今日の謎 | 大人向けの謎（ずらし暗号・和文化など） | practice | ソフト | なし |
| 金 | 遊び方 | ホーム画面に追加する方法など、つまずきやすい所 | objection | ミディアム | あり |
| 土 | 大人の脳トレ時間 | 自分で解いた感想・続けるコツ（効果の断言はしない） | problem | ソフト | なし |
| 日 | 今週のおすすめ | どちらかのゲームを1つ紹介 | offer | ハード | あり |

- CTAの強さは ソフト5：ミディアム1：ハード1（軍配の初期値 7:2:1 に近い配分）。
- リンク付きは週2本。XのAPI料金はリンク付きが1本約$0.20、リンクなしが約$0.015なので、この配分で**月およそ$2**（予算上限の初期値は月$3。本人判断事項）。
- 投稿時刻（毎日20:17）は保護者が一息つく時間帯を狙った**勘**。週次の数字を見て変える。

## 6. 止め方・戻し方

- **すぐ止める**: `_marketing/sns/config.json` の `mode` を `paused` にする（GitHubの画面で1行編集）。
- **1本だけ取り下げる**: 在庫の `queue/` から該当ファイルを削除する。
- **「送信中のまま」警報が出たら**: SNSを見て、投稿されていたらファイルを `posted/` へ、されていなければ `queue/` へ移す（移すまで自動投稿は止まったまま＝二重投稿防止）。
- **撤退条件**（4週後の裁定で使う）: ①週の投稿が4週連続で3本以下（仕組みより話す時間が足りない）②在庫切れが月3回以上 ③Xのアカウントに制限がかかった。どれかに当たったら自動投稿を止め、手動投稿に戻して原因を判断ログに残す。

## 7. 軍配の点検で変わったところ

| 変更 | 理由（点検の指摘） |
|---|---|
| 主戦場は1つだけ（`channel` は単一値。X と Bluesky を同時に選べない作り） | F1: チャネルは並列に増やさない／P0〜P1で装備過多にしない |
| リンク先をプルダウン化し、リンク付きは週2本の輪番に | F2: XのAPI料金はリンク付きが約13倍 |
| 月の予算上限で自動停止 | F2: 金銭は本人判断。超えそうなら止めて知らせる |
| 投稿前に sending/ へ確保してコミット（at-most-once） | F9: 二重投稿は自動化への信頼を一撃で壊す |
| 「広告なし」をブロック表現に | F5: 事実台帳と矛盾（AdSense利用） |
| 承認は所有者本人が書いた下書きだけ | F3: 公開リポジトリでは誰でもIssueを書ける |
| 計測は週次の手動写しから（APIでの数字取得は作らない） | F4: サイトにアクセス解析がない。P0〜P1では計測装置を作り込まない |
| 自動コミットは在庫フォルダだけ | 試運転で見つけた不具合（キャッシュや設定まで巻き込んでいた） |
| 「★サイトを公開する.bat」が push 前にサーバー側の更新を取り込む | F14: ボットのコミットで手元からの push が拒否されるのを防ぐ |
